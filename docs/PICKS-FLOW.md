# 推股闭环 V3：断点续传 + 消息库 + 可变早盘名单

> 2026-10-28 修订（V2 的云端部分已上线 `d693bd35`）。本版吸收三条新约束：
> 1. 用户开 App 的时间不固定，**打开时必须补传没发出去的数据**；
> 2. 早盘名单在 09:30 前**可变**（夜里算出的名单会被早间消息推翻）；
> 3. 消息面**只要开 App 就实时采集**、算出受益/受损个股，并按天存进 GitHub 消息库。

## 0. 一句话架构

端上是「采集 + 实时计算 + 本地队列」，云端是「慢计算 + 定稿」；两端靠两个 GitHub 目录
（`开盘推股历史数据/`、`消息数据库/`）做**断点续传**，软件关掉不丢数据，下次打开接着传。

## 1. 两个持久化目录

| 目录 | 内容 | 写入方 | 读取方 |
|---|---|---|---|
| `开盘推股历史数据/YYYY-MM-DD.json` | 盘中每轮推送（picks + base + data + note） | 端上 | 午盘脚本（11:40） |
| `消息数据库/YYYY-MM-DD.json` | 每条消息 + 情绪 + 利好质量 + 受益/受损个股 | 端上 | 早盘二次分析、午盘、收盘复盘 |

两个文件都按天累积，端上每次 flush 只追加不删（同一轮重复写入以 `ts` 去重）。

## 2. 时间线（修订）

```
【任意时刻打开 App】
  1. flush：把本地队列里没传出去的消息 / 推送记录补传到 GitHub
     - 先 GET 当天文件，有就合并（按 ts 去重），没有就新建
  2. 采集：拉一轮消息 → NewsCalcEngine 算受益/受损 → 入本地队列
  3. 状态判断：
     - 今天早盘名单已冻结（>09:30）→ 直接展示，不再重算
     - 今天未到 09:30 且已有草稿 → 用消息再算一轮，覆盖草稿
     - 今天还没有 → 拉云端 A/B 候选，生成草稿

【T+1 09:00–09:30 早盘窗口】
  - 实时收这 30 分钟的消息
  - 09:00 之前的消息从 `消息数据库/YYYY-MM-DD.json` 取
  - 若消息库覆盖不足（前一夜没开 App）→ 本地补拉历史消息（见 §5）
  - 每轮重算早盘名单：A/B 候选 ∩ 消息受益股 → 排序，**允许随时变化**

【09:30 冻结】
  - 写 `premarket_frozen_<date>` 标记，之后只读
  - 冻结后仍继续收消息（进消息库），但不再改早盘名单

【09:30–15:00 盘中】
  - 开盘推股名单：全市场实时 + 早盘名单 → 每轮更新（可变）
  - 每轮结果入队 → flush 到 `开盘推股历史数据/`

【11:40 云端】
  - 读推送历史 + 消息库 → 午盘名单（12:00 后固定）

【15:00 后 / 收盘】
  - 本地 flush 收尾，补 `mode=final` 一轮
  - 云端 15:30/16:40 出 A/B 候选，回到起点
```

## 3. 消息处理（端上已有能力，直接复用）

`NewsCalcEngine`（`engine-runtime`）已实现完整链路，**不重写**：

| 能力 | 位置 |
|---|---|
| 情绪判定（pos/neg/neu + 命中词） | `sentimentOf` |
| 利好质量（真利好 / 利好·防追高 / 利空 / 中性） | `verdictOf` |
| 标题 → 股票代码（代码优先，名称兜底；已修「2026 年→002026」误识别） | `resolveStocks` |
| 逐条实时打分（中枢引擎分 + 共振比 + 理由） | `compute` |

新增的只是**搬运**：把 `NewsCalc` 结果落到 `消息数据库/`，以及从库里读回历史消息。

消息库条目字段（与 `NewsCalc` 对齐，少存冗余）：

```json
{
  "ts": "2026-10-29T09:12:00+08:00",
  "src": "东财724",
  "title": "……",
  "sentiment": "pos",
  "verdict": "真利好",
  "impact": ["600000"],
  "themes": ["算力"],
  "boards": ["通信设备"],
  "status": "ok"
}
```

`impact` 为空时也要落库（`status=no_stock`）——「受益/受损个股没识别出来」本身是信息，
早盘二次分析要知道「这条消息没落到具体票上」，而不是当它不存在。

## 4. 端上新增模块

| 模块 | 职责 | 放哪 |
|---|---|---|
| `GitHubRepoWriter` | PUT/GET 仓库文件，带 `sha` 条件更新（冲突时重试） | `engine-net` |
| `PicksArchiveQueue` | 消息 / 推送记录的本地队列 + flush（按 ts 去重、失败保留） | `engine-runtime` |
| `PremarketPicks` | 早盘名单：草稿 → 09:30 冻结标记 | `engine-runtime` |
| 打开时 flush 钩子 | `SkappViewModel` 启动流程里插一步 | `ui` |

写入节流：消息 5 分钟一次、推送记录 5 分钟一次、收盘各补一轮 `final`。按当前频率
一天约 80–100 次 PUT，远低于 GitHub 5000/h 限制；同一文件用 `sha` 条件更新避免互相覆盖。

## 5. 消息缺口怎么补

早盘窗口开始时按「消息库覆盖到几点」判断：

- 覆盖到 ≥08:50 → 正常，只用库里 + 实时 30 分钟
- 覆盖不足（例如只到昨天 15:00）→ 两条路并行：
  1. 消息源的历史接口（东财 724 / 同花顺实时新闻多数支持近期回溯，能拉多久拉多久）
  2. 云端 `news_impact.json`（每日 17:10 更新）作为「昨日盘后消息」的兜底
- 补不到的部分在早盘名单里标 `dataGap`，并在界面上写明「消息面缺失 X 小时」，
  **不拿缺失当无消息**

## 6. 与云端的分工（不变的部分）

| 环节 | 端上 | 云端 |
|---|---|---|
| 全 A 收盘分析 → A/B 候选 | 不用 | 15:30/16:40（已上线） |
| 早盘名单 | 09:00–09:30 算，09:30 冻结 | 不参与（云端 `premarket_picks` 仅参考） |
| 盘中实时名单 | 每轮算 | 不参与（云端算不动） |
| 午盘名单 | 提供推送历史 + 消息库 | 11:40 读两个库算出（已上线） |
| 收盘复盘 | 提供推送历史 | 读历史评分 |

## 7. 分阶段实施

**P0（已完成）**：云端 A/B 候选、午盘 E、两个目录的格式约定

**P1（已完成）**

7. 缺口补拉：消息库覆盖不足且未冻结时，从消息源再拉 100 条重算

## 8. 风险

- **端上写 GitHub 失败**（无网/限流）：队列必须能跨重启保留（SP 或文件），不能只在内存
- **SHA 冲突**：同一文件被云端 CI 和端上同时改 → 用 `sha` 条件更新 + 重试一次，仍失败就留到下一轮
- **09:30 冻结**：必须落盘标记而不是靠内存状态，否则杀进程重开会被当成「未冻结」重算
- **消息量**：开 App 就采，长开一天会产生大量条目；按天分文件 + 只存精简字段（不存原文全文外的冗余）
