## 2026-10-27 晚 更正：聪明钱份额的口径结论错了，已改正

用户质疑「不会先去东财网页版看看有没有、再 F12 抓接口吗」—— 这次质疑是对的，我原来的结论有两处错：

| 我原来的说法 | 实际 | 证据 |
|---|---|---|
| 份额只能靠 push2 实时快照逐日积累，历史不可回填 | **错**。交易所每日披露 ETF 总份额，可回溯约一年，已回填 231 个交易日 | 上交所「ETF规模」页 `query.sse.com.cn/commonQuery.do?sqlId=COMMON_SSE_ZQPZ_ETFZL_XXPL_ETFGM_SEARCH_L&STAT_DATE=YYYY-MM-DD`，字段 `TOT_VOL`（万份）；实测 2025-09 起仍有数据 |
| 我估算的 352 亿份比季报 241 亿份偏高 46%，估算口径有问题 | **误判**。季报 241.20 亿份是 2026-09-30 的时点值，交易所 2026-10-23 真值就是 352.43 亿份；我的估算 352.31 亿份误差仅 0.03% | 上交所 10-23 `TOT_VOL=3524268.77` 万份；天天基金 `gmbd_510300` 季报表 2026-09-30 期末 241.20 亿份 |

改法：
- `collect_etf_shares.py` 份额主序列改交易所真值（上交所 `TOT_VOL` + 深交所 `scsj_fund_jjgm/current_size`，均万份→亿份）。深交所接口长区间会返回非 JSON，按 80 天分段请求。
- 旧的「成交量/换手率」估算降级为 `live_series` 对照字段，不再参与信号（混进真值序列会让 20 日变动算出 11257%）。
- `--backfill-days N` 支持一次性回填；已回填 231 天（5 只沪市），`smart_money.position_pct = 38.0`、`etfs_used=5`、`window_days=231` —— **仓位信号现在就是可用的**，不必等 20 天。
- App 侧 `SmartMoney.kt` 只认 `series` 里 `source` 为 `sse_*`/`szse_*` 的交易所真值点，阈值改读云端 `min_history_days`。

当前读数（2026-10-26）：510300 354.47 亿份（日 +0.58%、5 日 +21.41%、20 日 +49.82%）、510050 126.57 亿（5 日 +31.57%）、512100 110.17 亿（20 日 +72.49%）、588000 852.30 亿（5 日 +19.05%）、510500 70.52 亿（5 日 +10.52%）—— 宽基集体大额净申购，篮子处 231 日区间的 **38% 分位**。

## 2026-10-27 第二轮：把云端已有的标定与验证接进引擎链路

云端仓库里有一堆「算好了但 App 从没读过」的东西：weight_calibration（v3 标定，5~6 万样本、
16 指标 × 4 持有期）、walkforward（45 折样本外）、rps_rotation、market_breadth_history……
App 只用到了其中 3 个文件，择股阈值还是写死的。这轮接了三处。

### 1. 数据层：CloudFeed 统一入口

原来每个模块自己拼 URL、自己开连接；`EngineFeed.loadAll()` 串行拉 8 个文件，任何一个卡住
就整轮超时，失败还只是静默丢进 `missing`。现在统一成：

```
Doc 注册表 → 并发拉取 → 内存缓存(TTL 10min) → 按文件自身 ts 判陈旧 → 失败退回旧快照
```

三种状态明确区分：`json==null`（拉不到）、`stale=true`（拿到了但云端没更新）、正常。
`EngineFeed` 已切过来，单文件挂掉不再连累其它七个。

### 2. 算法：FactorWeightStrategy（云端权重 × 端上指标）

16 个指标端上基本都有实现（Donchian/UltimateOsc/Choppiness/CMO/Keltner/VWMA/A-D/HullMA/
Pivot/MA/SuperTrend/ElderForce/Vortex/RSI + 本地补的 MACD/RSV），缺的是**权重从哪来**。
现在直接读云端 `rel_weight`（Donchian20 0.5 → RSI 0.1，差 5 倍，不做等权平均）。

关键取舍：**这套东西不能用来选股**。云端数据写得很清楚——16 个指标 edge 全为负
（−5 ~ −7pp）、bull_win_rate 只有 43~45%、`market_advice=avoid_first`。所以输出只有
`AVOID / WATCH / PASS` 三档，PASS 的含义是「本模块没有否决它」，不是看涨。

> 第一版实现给三只上涨的样本票都打了「可买」，正好违背云端这个结论，已改掉；
> 测试现在断言的是「下跌趋势的票必须被否决」。

顺手修了 `ExtendedIndicators.superTrend`：上轨/下轨写反了（`basicUpper = hl2 - mult*atr`），
策略里改用本地修正版，原函数没动（详情页还在用它的值）。

### 3. 链路：SignalCalibration（样本外 + 市况 → 真正的闸门）

之前 walkforward 和 avoid_first 只是躺在 json 里。现在变成两个系数：

| 系数 | 依据 | 取值 |
|---|---|---|
| confidence | 沿用云端自己的「OOS < IS − 10pp 判 overfit」规则分档 | 1.0 / 0.85 / 0.75 / 0.7（无数据 0.8） |
| buyFactor | `market_advice=avoid_first`，且 16 指标看多胜率全 < 50% | 0.85 |
| positionFactor | confidence × buyFactor | **只减不增** |

决策页的仓位链路因此变成三段，每段都标出来源：
`云端基准上限 → ① ETF 份额调档 → ② 校准闸门 → 校准后上限`。

`applyCap` 是「基准 → 校准后」的一次映射，**不能叠加调用**（会 0.85² 重复打折），
测试断言的是单调不增而非幂等，注释里也写死了。

### 4. 引擎测试进 CI

`:engine` 原来没有 test 源集，CI 只做 `compileKotlin` —— 编译通过挡不住「权重解析成等权」
或「均线空头排列读成买点」这类方向性错误。现在有 6 个用例跑真实 140 根日 K
（688655/002230/600519/601398）+ 真实云端标定 fixture，CI 的 engine gate 里跑 `:engine:test`。

## 2026-10-27 第三轮：因子去相关 + 板块主线

### 1. 「14 个偏多」其实是同一句话说了 14 遍

上一轮交付的逐指标加权，在四只样本票里有三只出现「14 个偏多 / 0 个偏空」。看着像 14 份独立证据，
实际是共线：Donchian 位置、Keltner 位置、Pivot 都在回答「价格站在区间哪一侧」。

**第一次改法是错的，测试把它抓出来了**：族内加权平均 × 族权重（= 族内权重和/总和）是恒等变换，
四只票的分数和改之前一字不差。这个坑现在写在 `aggregate()` 的注释里，并且有一条用例钉住
「族内指标从 1 个变 5 个，结论不变」这一性质。

真正有效的改法：

| 规则 | 效果 | 用例 |
|---|---|---|
| 每族一票，族间等权 | 5 个趋势指标同向 = 1 个趋势指标同向 | `族内指标数量不影响结论` |
| 族内分歧按 (1 - dispersion) 打折 | 3 多 2 空 → 净额接近 0 且票变轻，而不是既算 3 份多又算 2 份空 | `族内分歧要让这一票变轻` |
| 单族翻脸上限 1/5 = 0.2 | 够不到 0.30 的 AVOID 线，只能进 WATCH | `单族翻脸不足以否决` |

族间取等权是有意的：云端 `rel_weight` 是**指标层**标定，没有族层标定。用「族内权重之和」当族权重，
趋势族（5 个指标）天然压过量能族（2 个），正是要去掉的偏差。

旧口径保留在 `Score.rawBuyScore/rawAvoidScore`，改动可对照、可复算。

### 2. 板块主线：并列的第二道过滤，不混进加权分

`sector_engine` 给 27 个板块的 B/C/D 分档、主线名单、回避名单，但**没有给「B 档板块的个股
次日胜率」**这种标定。没有标定就编个权重塞进加权求和，等于把刚做的事倒退回去。
所以只做并列过滤：因子 AVOID 或板块规避 → 双重否决；因子 PASS + 板块主线 → 共振；
两者矛盾 → 界面直说矛盾，不替用户裁决。

### 3. 个股→板块的 join 根本是坏的（这是数据问题）

实测：

| 数据源 | 层级 | 规模 | 能落到 27 个板块的 |
|---|---|---|---|
| `industry_map_em.json` | 东财三级 | 1050 只 / 80 行业 | **14 只（1.3%）** |
| db-market `industry.json` | 东财一级 | 3864 只 / 100 板块 | 8/27 个板块 |
| `concept_map.json` | 概念 | 180 概念 | 22/27 板块，但每板块只有 1 只代表股 |

三套体系层级不同，名字模糊匹配只会错配（「家纺」并进「服装家纺」）。所以端上**不做模糊匹配**：
`SectorLink` 报 `MapSource` 和覆盖率，只有兜底源时界面直接警告。

真正的修复在云端新增 `scripts/build_stock_sector_map.py`：用全市场列表自带的 `f100` 行业字段
（与 sector_engine 同一套命名）一步建映射，不做任何名称匹配，挂在 sector-constituents 工作流上每日重建。

> 采集过程本身踩了两个坑，都记在脚本注释里：`fs=m:90+t:2` 在 runner 上返 502（改走全市场 f100）；
> 东财翻到第 8 页开始 502，旧代码直接跳出整轮 + 1000 只门槛，结果一个文件都没产出
> （改成逐页重试跳过 + 门槛 500 + coverage_note 如实标注）。

本轮新增/保留待办：
- 云端还有一批算好但尚未接入的数据：theme_report（题材）、pead_events（财报漂移）、valuation、limitup_forecast、market_breadth_history —— 下一轮优先接 pead 与 limitup
- 去相关是「按指标定义分族」，不是按数据算相关性（那需要全市场因子矩阵，端上不做）；若云端能出因子相关性矩阵，族的划分可以更准

### 2026-10-30 第二轮：书籍权重从常量改为规格驱动（缺键即停用）

上一轮的 `W_BOOK = 0.6` 有两个问题，其中一个当场就定型了事故面：

1. **不受云端控制**：调权重、回滚权重都得发版，等于把「书籍票抬多少分」交给 APK。
2. **「只投 +1 ⇒ 只抬分」是错的直觉**：中枢是 `(Σ w·vote·strength)/(Σ w)`，新票贡献
   `w·(s − base)/(den + w)`，`s < base` 时**加票会压分**。所以权重一旦不可调，就没有任何
   手段在不发版的情况下纠正方向。

改法（**最终口径 = 保守口径 + 完整口径叠加**）：

> 同一时间窗口内，另一个执行体把「完整口径」也落了地：云端 `data/engine_spec.json` 升到 **3.1.1**，
> `device_engines` 19 项（含 `book`），`weights.book = 0.6`；端上资源与 `BUNDLED_VERSION` 已同步。
> 所以现在两条一起生效：**规格里真的有 book 权重了，且它由云端控制**。

- 删除 `W_BOOK`，改 `bookWeightOf(spec) = spec.weights["book"] ?: 0.0`；
- `externalVotes` 准入口径从「写死生效」改为「规格登记了 `weights.book` 且 > 0」；
- 缺键时**不计票**（不是靠 0 权重稀释），并在 `degraded` 写「书籍层：规格未登记 book 权重，已停用不计票」；
- 传给 `CanonicalEngine` 的 `weights["book"]` 显式写 0.0 —— 不能靠省键，省键会 fallback 到 **1.0**
  （`CanonicalEngine.score` 的 `w[v.indicator] ?: 1.0`），那是把权重放大而不是关掉。
- 自检新增两条不变量：「书籍权重缺键即停用」「书籍权重登记即生效」，替换原来的「W_BOOK ∈ (0,1]」。
